# Audit 0.372.0 — pastille de l'application installée (App Badging), fichier .reg de l'adresse sûre

Date : 27/10/2026. Relecture en lecture seule du dernier commit (0.372.0) : `client/130-pastille-application.js` (nouveau, lu en
entier), `client/122-notifications.js` (`tourPastille`, `renderReglagesNotifications`), `client/manifest.json`, `index.html`,
`server/src/verificationsTerrain.js`, `tests/notifications.test.js` ; lus aussi pour le contexte : `sw.js`, `manifest.json`,
`client/37-nas-notifications-pieces.js` (enregistrement du service worker), `client/114-canaux.js`, `client/112-routines.js`,
`client/129-messages-claire.js` (relevés fenêtre cachée), `client/41-reglages.js` (`noterVerificationPoste`),
`server/src/installationPoste.js` (fenêtre `--app`). Aucune donnée client dans ce rapport.

Rôle : architecte logiciel senior et expert en cybersécurité. Axes : sécurité, qualité et architecture, performance, conformité.

## Verdict global

**Correct avec réserves.** Aucun point Haut. Le code est court, sans route serveur nouvelle ni donnée nominative : la page pose un
nombre sur l'icône, le fichier .reg ne contient que l'origine du serveur (filtrée caractère par caractère, test d'injection à l'appui),
écrit en UTF-16 LE avec BOM, format accepté par regedit. Les réserves tiennent à ce que le fichier .reg fait au navigateur du poste
(l'adresse http tenue pour sûre par tout Chrome/Edge de la machine, pour tous les profils et tous les utilisateurs), et à deux
défauts de fonctionnement : sans relais, une fenêtre cachée ne relit plus les compteurs (la pastille se fige justement quand elle
sert), et une fenêtre `--app` (raccourci CLAIRE actuel) peut être prise pour l'application installée.

## Ce qui est bien fait

- Injection dans le .reg impossible : l'origine est réduite à `[A-Za-z0-9:/.\-[\]]` (ni guillemet, ni antislash, ni retour à la
  ligne, ni `=`), donc ni nouvelle clé ni nouvelle valeur ; les antislashs des noms de clés sont simples dans le fichier produit ; une
  adresse IPv6 entre crochets passe ; tous les caractères restent sous U+0100, l'encodage UTF-16 LE octet par octet est exact.
- Le chemin de la stratégie est le bon pour Chrome (`HKLM\SOFTWARE\Policies\Google\Chrome\OverrideSecurityRestrictionsOnInsecureOrigin`)
  et pour Edge (`…\Microsoft\Edge\…`), en liste de valeurs chaîne.
- Aucune route serveur, aucun secret, aucune donnée nominative : seul un nombre part vers l'icône ; le texte affiché passe par
  `escapeHtml` ; le bouton est un `wa-button` outlined ; l'appel est coupé dans la fenêtre du poste de CLAIRE (`POSTE_CLAIRE`) ;
  `setAppBadge` n'est rappelé que si le nombre change (mémo `etatBadgeApplication.pose`), le réglage « pastille » éteint retire la
  pastille.
- Fichier du poste déclaré dans `client/manifest.json` et `index.html` ; point de « Vérifications sur le terrain » ajouté.

## Non vérifiable ici

Rien de cette nouveauté n'a tourné dans un vrai Chrome ou Edge Windows : installation de l'application sur une adresse http tenue pour
sûre, pastille dans la barre des tâches, prise en compte de la stratégie sur un poste non joint à un domaine (Chrome ignore certaines
stratégies sur une machine non gérée — à confirmer pour celle-ci), import du .reg par regedit.

## Suite donnée

- Relevés fenêtre cachée : `pastilleActiveHorsEcran` est vrai aussi quand l'application pose sa pastille (`pastilleApplicationActive`).
- Fenêtre `--app` prise pour l'application : le point `pastille-application` passe en « manuel » (« C'est bon » quand la pastille se voit), et
  le texte « Prête » dit que la pastille n'apparaît que sur l'icône de l'application installée.
- Changement de collaborateur : `oublierPastilleCollaborateur` retire la pastille.
- Refus de `setAppBadge` : plus d'essai dans la fenêtre, `console.warn` (journal technique), état « navigateur » dans les Réglages.
- Message « adresse » : `edge://flags` dans Edge ; un navigateur qui n'est ni Chrome ni Edge reçoit « navigateur », sans le bouton du .reg.
- Relais et application sur le même poste : le relais reçoit un total à 0 quand l'application pose la sienne (ses notifications restent).
- Service worker : tout service worker qui n'est pas `/sw.js` est retiré au démarrage (client/37). Entrée « 1 » de la liste : le texte
  des Réglages demande à Fichorga d'ajouter l'adresse à sa liste s'il pose déjà cette stratégie.
- Portée de la stratégie (adresse http « sûre » pour tout le navigateur du poste) : dite à l'étude ; la vraie réponse reste HTTPS avec une
  autorité interne.
- Non retenu : le gestionnaire `fetch` vide de `sw.js` reste (critère d'installation des versions de Chrome des postes, non vérifiable ici).
- Tests : encodage UTF-16 extrait en `octetsUtf16Reg` et testé ; `poserPastilleApplication` (DOM, navigator) n'a pas de test unitaire.

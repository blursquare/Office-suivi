# Audit et relecture indépendante — CLAIRE 0.403.0 (30/10/2026)

Périmètre : diff non commité de la 0.403.0 (« vrai agent », étapes 3 à 5) — `client/132-artefacts-agent.js` (`envoyerMailAgent`),
`client/143-assistant-reglages.js` (nouveau, `modifierReglageAgent`), `client/61-assistant-agent.js`, `client/114-canaux.js` +
`client/49-assistant.js` (`claireDoitRepondreCanal`, `responsableDuCanalEstMoi`), `server/src/assistantAgent.js` (outils `envoyer_mail`,
`modifier_reglage`, prompt), `server/src/routines/{executants,catalogue,planificateur}.js`, `server/src/app.js` (`documentsDossier`),
tests `server/test/routines-etape4.test.js`, `tests/canaux.test.js`. Les deux suites de tests touchées passent (0 échec). Chaque point
ci-dessous a été vérifié dans le code et, pour les routines, rejoué avec `node -e` sur des dossiers inventés.

## Verdict global : correct avec réserves

Aucun point « Haut ». Le chemin d'envoi d'un email par l'agent est sûr : carte stricte à chaque fois, refus sur l'ordinateur de CLAIRE
côté poste et côté serveur, seul le brouillon de l'artefact cité peut partir. Les réglages hors liste blanche ne peuvent pas être
modifiés. En revanche, les quatre nouvelles routines sont allumées par défaut et produiront beaucoup d'alertes dès le premier tour.
Deux règles de droit sur les diagnostics sont fausses ou trop larges. Une relance continue pour une pièce que l'étude a retirée.
Il vaut mieux corriger les points « Moyen » avant la publication, surtout M1, M2 et M4 : le 27/10, l'étude avait déjà dit « on en reçoit trop ».

### Règles de CLAIRE vérifiées (conformes)

- **`envoyer_mail` jamais couvert par « Autoriser pour toute cette demande »** : `demanderAutorisationAgent(…, { strict: true })`
  (client/132:126) ; en mode strict, `client/66` ne saute pas la carte et n'offre pas le bouton « pour toute cette demande ».
- **Jamais depuis l'ordinateur de CLAIRE** : `if (POSTE_CLAIRE) return { erreur }` (client/132:117). De plus, `/api/emails/envoyer` est
  absent de `PERMIS_ECRITURE` (server/src/posteClaire.js:34) et refusé par le serveur.
- **Jamais un autre brouillon que celui montré** : `brouillonDeArtefact(a)` n'accepte que la rédaction dont `artefactId` est celui
  de l'artefact. L'identité est revérifiée après le clic (`brouillonDeArtefact(a) !== r`). Les outils s'exécutent un par un
  (client/61:434, `await` dans la boucle) : une correction `artefact` du même tour ne peut pas changer le texte pendant que la carte attend.
  Un second appel après l'envoi échoue, car la fenêtre est fermée : il n'y a pas de double envoi.
- **« [à compléter] », WeTransfer, plus de 21 Mo, sans Exchange** : `etatEnvoiRedaction()` / `envoiDirectPossible()` refusent avant la carte.
- **Liste blanche des réglages** : `REGLAGES_AGENT = ['routine','source_web','index_nas']`, avec une énumération côté schéma. Le PUT
  `/api/routines/reglages` n'envoie que `{ routines: { id: { actif } } }`, fusionné clé par clé côté serveur
  (`routes/routines.js:50-53`). Aucun niveau d'autonomie ne peut être monté par l'agent. La bascule d'une routine reste soumise
  au contrôle administrateur du serveur (403 sans `auteur` administrateur).
- **Rien de nominatif vers une IA** : les quatre routines n'appellent pas d'IA. Les résultats des deux outils passent par le masquage
  générique des résultats d'outils. Les cartes passent par `escapeHtml` (`htmlAutorisationAgent`).
- **Dossier abîmé, archivé ou signé, succession, participation, date absente** : `dossierOuvert` écarte les dossiers archivés et signés.
  Les routines du rendez-vous et des relances écartent les successions et les participations. Toutes les dates passent par `estIso`.
  Les listes sont lues avec des valeurs par défaut. Aucun plantage n'a été obtenu sur des dossiers incomplets.

## Explications et remédiations (points Moyen)

### M1 — Bruit des nouvelles routines

**Constat.** Rejoué : une vente avec signature au 20/01/2027, vue le 30/10/2026, sans aucun autre problème, donne l'alerte
« Signature du 20/01/2027 : 1 point à vérifier — 11 pièces encore manquantes ». C'est le cas de presque toutes les ventes dès que
le rendez-vous est posé, et la revue du matin dit déjà la même chose à J-21 (`revue:pieces`). Une succession sans mouvement depuis le
01/09 donne « Rien de neuf depuis 59 jours ». Une vente qui attend son offre de prêt pendant 45 jours, ou dont tout est prêt avec un
rendez-vous dans deux mois, sera elle aussi déclarée « n'avance plus ». `derniereActiviteDossier` ne voit ni les emails, ni les
messages du canal, ni les relevés d'Authentic. Les quatre routines sont `allumeeParDefaut` : le premier tour, à 8 h, dépose tout
d'un coup dans les canaux.

**Correction.**
```js
// incoherencesSignature : les pièces seulement près de la signature (la revue du matin dit déjà le reste)
const { manquantes } = piecesRecuesEtManquantes(d);
if (manquantes.length && joursEntre(aujourdhui, rdv) <= JOURS_PIECES_AVANT_RDV) pb.push({ cle: 'pieces', … });
// (passer `aujourdhui` à incoherencesSignature)

// dossiersBloques : pas de succession, rien quand un rendez-vous est déjà placé, rien tant qu'une échéance à venir est attendue
if (!dossierOuvert(d) || estSuccession(d) || estIso(d.rendezVousSignature)) continue;
const attentes = P.echeancesPlanning(d).filter((e) => e && !P.echeanceValidee(d, e.type));
if (attentes.some((e) => estIso(e.iso) && joursEntre(aujourdhui, e.iso) >= 0)) continue;   // on attend une date : normal
```
Allumer les deux routines d'alerte (`dossiers-bloques`, `emails-recus`) **éteintes par défaut**, ou plafonner le premier tour (par
exemple, ne déposer que les dossiers dont l'immobilité a commencé depuis la mise en service).

### M2 — Relance d'une pièce retirée ou d'une préemption levée

**Constat.** Rejoué : un dossier avec `piecesRetirees: ['renonciationPreemption']` et une DIA demandée le 01/08 donne la tâche
« Relancer : DIA » le 30/10, puis une nouvelle tous les 15 jours. Même chose quand le DPU est « non » (`droitNonApplicable`) ou que la
préemption est levée par une autre voie.

**Correction** (executants.js:451-454) :
```js
for (const [cle, dem] of Object.entries(demandes)) {
  if (!dem || !estIso(dem.date)) continue;
  if ((d.pieces || {})[cle] === 'recue' || (Array.isArray(d.piecesRetirees) && d.piecesRetirees.includes(cle))) continue;
  if (cle === 'renonciationPreemption' && P.preemptionLevee(d)) continue;
  …
```
Ajouter le cas au test `routines-etape4`.

### M3 — Diagnostics lus dans le résumé libre

**Constat.** `v.re.test(sansAccents(`${x.type} ${x.resume}`))` : le résumé d'une phrase écrit par l'IA cite souvent les diagnostics
d'un autre document. Rejoué : `{ type: 'compromis de vente', date: '2026-02-01', resume: 'Compromis signé, DPE, ERP et état termites
annexés' }` donne « ERP » et « termites » périmés au 01/08/2026. De même, une facture d'électricité ancienne de plus de 3 ans devient un
« Diagnostic électricité » périmé. « assainissement » désigne aussi un courrier de la mairie sur l'assainissement collectif, qui n'a
pas de durée de validité légale.

**Correction.** Ne juger que le **type**, qui doit nommer un diagnostic :
```js
const t = sansAccents(x.type);
if (!/(diagnostic|constat|etat|dpe|erp|rapport|controle)/.test(t) || /(compromis|promesse|facture|acte|courrier)/.test(t)) continue;
// et pour l'assainissement : seulement « non collectif » / « spanc »
{ re: /(non collectif|\bspanc\b|\banc\b)/, mois: 36, nom: 'Contrôle de l’assainissement non collectif' },
```

### M4 — DPE d'avant le 01/07/2021

**Constat.** Rejoué : un DPE du 01/05/2019 n'est pas signalé pour une signature au 20/11/2026, alors qu'il n'est plus valable depuis
le 31/12/2024 (décret 2020-1610 : DPE de 2013 à 2017 jusqu'au 31/12/2022, de 2018 au 30/06/2021 jusqu'au 31/12/2024).

**Correction** :
```js
function finValiditeDpe(date) {
  if (date < '2018-01-01') return '2022-12-31';
  if (date < '2021-07-01') return '2024-12-31';
  return plusMois(date, 120);
}
// diagnosticsPerimes : const fin = v.nom === 'DPE' ? finValiditeDpe(derniere) : plusMois(derniere, v.mois);
```
Écrire aussi chaque ligne au conditionnel « à vérifier » (voir B3).

### M5 — Carte non stricte pour les réglages qui changent les flux de données

**Constat.** `demanderAutorisationAgent(texte)` est appelée sans `strict`. Si l'utilisateur a cliqué plus tôt dans la même demande
« Autoriser pour toute cette demande », `client/66:53-57` accepte d'office. Un document ou un email lu dans la même demande (texte non
fiable) peut alors faire allumer l'index du NAS, qui envoie un flux automatique de textes vers Anthropic, ou ajouter `site-piege.fr`
aux sources de la recherche web pour toute l'étude, sans nouvelle carte. Cela contredit la description de l'outil (« Carte "Autoriser"
à chaque changement »).

**Correction** (client/143:45, 58, 65) :
```js
const ok = await demanderAutorisationAgent(`…`, { strict: true });
```
Garder éventuellement le mode non strict pour l'extinction seule (`eteinte` / `eteint` / `retirer`), qui ne réduit rien.

## Points Bas — remédiation courte

- **B1** : ajouter à `VERIFICATIONS_TERRAIN` les points `agent-envoyer-mail` (source poste) et `routines-controle-rendez-vous`,
  `routines-dossiers-bloques`, `routines-emails-recus`, `routines-relances-formalites` (source serveur, depuis `0.403.0`), ou noter
  `agent-proactif`.
- **B2** : borner le jour : `const d = new Date(Date.UTC(a, m - 1 + mois, 1)); const dernier = new Date(Date.UTC(d.getUTCFullYear(), d.getUTCMonth() + 1, 0)).getUTCDate(); d.setUTCDate(Math.min(j, dernier));`
- **B3** : par exemple « l'offre est attendue au plus tard le … : le délai de réflexion (10 jours, acceptation au 11e) risque de ne
  pas tenir — à vérifier » ; « ERP du … : au-delà de 6 mois le jour de la signature, à refaire — à vérifier ».
- **B4** : n'alerter que sur les sujets `offre`, `fonds`, `rib`, `projet`, `urgent`, ou sur une pièce jointe PDF. Sauter un email déjà
  traité par `reponses-emails` (clé `routines-emails-traites`).
- **B5** : `if (r.envoi) return { erreur: 'envoi déjà lancé par l’utilisateur' };` avant la carte, et ne pas conclure « non envoyé »
  quand `r.envoi` est vrai.
- **B6** : renvoyer `{ erreur: 'routine pas encore disponible' }` si `!r.disponible`. Le contrôle administrateur serveur de
  `/index-nas/reglages` s'aligne sur le reste des Réglages (piste générale).
- **B7** : une piste serait de ne répondre sans « @ » qu'aux messages qui se terminent par une question ou commencent par un verbe de
  demande. À laisser à l'étude.
- **B8** : retirer `cleePiece` ; sortir `PREFIXES_SUJETS` en constante ; une fonction `ctxRoutines()` commune aux deux appels du
  planificateur ; corriger le libellé du déclencheur.
